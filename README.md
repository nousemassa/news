# Проект `news` — бот канала новостей

**Что это.** Новостной контур целиком: бот канала (`news_agent.tg.news_bot`), процесс выпуска
(`news_agent.news_main`, порт `8086`), разбор ленты (`news_agent.news`), команда ролей на LangGraph
(`news_agent.news_team`) и измерение её решений (`news_agent.decisions`).

| Что | Где |
|---|---|
| HTTP-процесс (`/health`) | `127.0.0.1:8086`, имя службы `news` |
| Своя база | `news-db:5432/news` — служба `news-db` этого композа, том `news-db-data`; логин и пароль — в `.env` проекта |
| Векторы (чтение) | `pgvector:5432/vectors` — база проекта `realty` |
| Эмбеддинги, решатель | `embed:8082`, `solver:8083` — адреса объявляет `.env` агента |
| Поиск | `mcp-searxng:3000/mcp` |

## Как запускать

```bash
make up        # поднять и дождаться готовности (Telegram + канал)
make status    # показать состояние
make stop      # остановить (тома и данные не тронуты)
make check     # офлайн: композ разбирается настоящим парсером
make test      # офлайн-тесты (живые пропускаются, если нет адреса тестовой базы)
```

## Контракт с остальными

* **Сеть — общая с платформой** (`external: true`, имя в `PLATFORM_NETWORK`): создаёт её стек платформы,
  проект её не создаёт.
* **Имя службы `news` и порт `127.0.0.1:8086` — внешний контракт**: сторож обвязки ходит именно туда, а
  хостовый лончер и юнит — откат.
* **Данные берутся по именам служб** (см. таблицу): это контракт сети, а не связь кода. Векторная база
  принадлежит проекту `realty`; новости её только читают, и эта граница названа осознанно.
* **Каталог сессий — свой** и задаётся настройкой `SESSIONS_DIR` (том монтируется в `/srv/news/.sessions`).
  Из расположения кода он не выводится: в установленном пакете этот путь указывал бы в `site-packages`,
  и бот **молча** не подключался бы.
* **Общего кода нет.** Всё, что нужно обоим контурам, живёт в `agent_core` и ставится колёсом
  (`wheels/agent_core-*.whl`); пакет проекта не импортирует пакет другого проекта.

## Решения

| Решение | Что этим исключено | Где видно |
|---|---|---|
| **Публикация — запись под сравнение-и-запись и кнопка владельца, а не автопубликация.** Новость забирается в работу одним `UPDATE … WHERE status='draft'` (`draft` → `publishing`), после успешной отправки в канал ставится `published` и дата. Дубль при перезапуске исключён самой атомарностью: в работу берётся только `draft`, второй раз тот же черновик не захватить. Залипшие `publishing` (процесс умер между захватом и подтверждением) возвращаются в черновики на старте бота, иначе новость навсегда осталась бы «Публикуется…». Публикует только человек: кнопки «Редактировать» и «Опубликовать». | Ошибочная публикация в канал, которую уже невозможно отменить, и дубль новости при перезапуске процесса. | `news_agent/db/repo.py` (`claim_news_publish`, `confirm_news_published`, `release_stale_publishing`); в боте — вызовы |
| **Команда ролей — узлы LangGraph, а не второй агентный фреймворк.** Исследователь → автор → проверяющий факты идут узлами графа; порядок и передача результата — наш код, фреймворк отвечает только за исполнение роли. Один фреймворк на проект, одно окружение. Боевой поиск сейчас идёт одиночным прогоном агента (`SEARCH_VIA = "agent"` в `tg/news_bot.py`), команда остаётся рабочей ветвью: её гоняют тесты, и переключение — правка одной строки. | Второе окружение ради второго фреймворка и постредактор вместо независимой проверки. | `news_agent/news_team/graph.py`, `roles.py`, `tg/news_bot.py` |

## Окружение

Значения читаются из `.env` рядом с композом (образец — `.env.example`) — этот файл обязателен.
Общий `.env` воркспейса, если проект стоит внутри воркспейса, лончер подключает ПЕРВЫМ, для подстановки
`${…}` в композе; в контейнер идёт только `./.env` проекта, поэтому всё, что нужно службе, должно быть
в нём.

| Ключ | Что задаёт |
|---|---|
| `DB_URL` | адрес своей базы с её логином и паролем |
| `VECTOR_DB_URL`, `VECTOR_DB_PASSWORD` | векторная база (чтение через границу проекта) |
| `LLAMA_EMBED_URL`, `SOLVER_URL` (+`_HOST` для хостового лончера) | адреса сервисов моделей — свои у агента |
| `TELEMETRY_OTLP_ENDPOINT` | адрес приёма трассировки (вендор приёма — ось `TELEMETRY_VENDOR`) |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | доступ к MTProto (my.telegram.org) — без них бот не подключается |
| `TELEGRAM_NEWS_BOT_TOKEN`, `TELEGRAM_NEWS_CHANNEL_ID`, `TELEGRAM_NEWS_OWNER_CHAT_ID` | транспорт публикации и адресат уведомлений |
| `UI_SECRET` (≥16 символов) | подпись кнопок «Редактировать»/«Опубликовать» — без него они не рендерятся |
| `SESSIONS_DIR` | каталог файлов-сессий (настройка, не вывод из кода) |
| `PLATFORM_NETWORK`, `PLATFORM_VENDOR` | имя общей сети и режим платформы |
| `NEWS_*`, `TEAM_*` | темп выпусков и состав команды |

## Чего здесь нет

* **Сторожей и юнитов** — наблюдение живёт в обвязке воркспейса, таймеры хостовые; этого репозитория
  они не касаются.
* **`--remove-orphans`** — запрещён: он удаляет контейнеры, которых нет в ЭТОМ файле.
* **Автопубликации** — публикует только человек, кнопкой. Локальный набор инструментов агента только
  читает; внешние MCP-инструменты приходят по настройке `TEAM_MCP_SERVERS`, поэтому их состав —
  предмет настройки, а не гарантия кода.
